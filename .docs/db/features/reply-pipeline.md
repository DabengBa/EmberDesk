# Feature: Reply Pipeline

## ID 解释

`feature.reply_pipeline` represents the preset-carried multi-step reply orchestration: one user turn is answered by an ordered sequence of logical steps (`analyze → review → respond`, author-defined). Each request forces the current step tool; an actual call or a nonempty text-only response is normalized to `submit_story({content: string})` as an internal carrier. It covers step normalization, per-round step instructions, request-only history projection, request shaping, the final-direct reply write, and the closing fallback round. It does not cover tool binding storage or the tool-call transport itself (see [Tool Bindings](feature.tool_bindings)).

## Purpose

Make reply structure deterministic instead of model-discretionary. Parallel tool calls cannot see each other, and free recursion lets the model skip, repeat, or reorder steps — so the order is orchestrated by the app, while the model only authors each step's content.

## Ownership Direction

The plan is saved with the preset in `oai_settings.reply_pipeline`. In OpenAI-compatible character chats and temporary Assistant chats, the server owns the run. The existing browser generation path remains for contexts outside that route.

## User-Visible Contract

- In an OpenAI-compatible character chat, the server owns the run and saves the final reply. Default steps continue even when the chat is closed or the page disconnects. A matching call to a custom script waits for that script to run in an attached browser; reopening the same chat resumes a waiting step. Stopping the run discards unfinished output rather than saving it.
- Send, regenerate, and continue use the active pipeline in saved character chats and temporary Assistant chats. Regenerate excludes the old generated reply; continue includes it as context and appends the new output to the same reply. A numbered step requires the matching tool call, not ordinary text.
- On the server path, completed steps appear in one temporary card. In a character chat the card is restored on reattachment, and only the final reply is saved, with the completed steps and any final-step option chips. A temporary Assistant chat keeps its final reply in the current view only. Recoverable failures retry only the current round, using the configured fallback model after the primary retry. The Prompt Inspector previews each step and the closing round without running scripts.

- `reply_pipeline` is preset-carried: `{ enabled, enforce_mode?: 'auto'|'forced', result_field?, final, steps: [{ tool, model?, prompt?, display?, max_tokens?, reasoning_effort?, id? }] }`. It is a `settingsToUpdate` field, so preset apply/save and the canonical settings document persistence all carry it; applying a preset without a `reply_pipeline` key clears the active pipeline.
- Disabling the pipeline prevents subsequent generations from sending tool definitions, while retaining the bindings for later re-enabling. An already-running pipeline finishes before the new setting takes effect.
- A blank or missing step model inherits the preset model. Each attempt resolves its model before building the request; fallback-provider recovery overrides the step, while the closing round normally uses the preset model and can itself recover using the fallback provider. A known tool-incompatible step model is rejected, not silently stripped; unknown names remain usable. The initial media/history prefix is assembled for the first step model and captured for the run, so later models and recovery attempts reuse that prefix even if their media capabilities differ.
- Recovery belongs to the failed pipeline round: previously completed tools and their captured results are not replayed. Each step's dedicated prompt tail is expanded once with its initial attempt model and reused unchanged on retries, even when the fallback request uses a different model; consequently `{{model}}` in that snapshot still shows the initial model. Other macros and their side effects are not repeated. The shared prefix and completed steps remain fixed. Final success, exhausted recovery, and cancellation release the run.
- `final` names the reply-producing tool; the plan is truncated at that step (steps after it are unreachable), and an unknown or missing `final` resolves to the last step. Plans are clamped to `MAX_PIPELINE_STEPS` (5 = `ToolManager.RECURSE_LIMIT`).
- Committing a valid step tool name on blur or Enter automatically creates an enabled, non-stealth text binding; typing alone creates no bindings. Explicitly enabling the pipeline or committing a name activates an existing binding without replacing its custom schema or action. Blank/invalid names create nothing.
- Settings load, preset apply, and initial runtime initialization repair missing bindings for enabled pipelines. Passive repair preserves existing disabled/stealth flags. Generated bindings require a string `content` argument and return that text directly, without another JSON string layer. Code-registered tools are never replaced by generated placeholders. Removing steps or disabling the pipeline retains user bindings.
- Steps whose existing bindings remain disabled or `stealth` are skipped; a pipeline with no runnable steps is inert.
- Each round appends one system instruction naming the step tool and its `prompt`. Shaping only applies to `type === 'normal'` request bodies and appends each round's material once, so retries do not duplicate it and quiet/raw/other generations never inherit stale step prompts, forced `tool_choice`, or step token caps.
- Within a run, the initial conversation is captured once. Later rounds append step-scoped material and instructions, then retain each accepted assistant tool call with its paired receipt without rebuilding earlier rounds from the live display card. The older browser path can also retain a text-only step response as text. Context overflow fails explicitly rather than silently trimming the captured prefix. This makes requests prefix-stable; actual provider cache reuse is not guaranteed.
- In a server-owned text turn with an active pipeline, only retained wrapped memory summaries are joined chronologically into one `story_history({content})`, without role fields or generated speaker labels. If no summary is retained, there is no `story_history` call. Earlier text messages not replaced by summaries remain separate `submit_story({kind, content, name?})` calls, preserving message order and the configured speaker-name format. The current text input is a separate `story_continuation_input({kind: 'user', content})` call whose ID is referenced by the step instruction. Each synthetic assistant call has an immediate `OK` receipt. Inlined media retains its native multipart message instead.
- The merged summary is sent at the first retained summary position. Preset prompts, character description, matched World Info and injections remain separate, and World Info activation is unchanged. Edited replies contribute their effective text once, not stale tool arguments, intermediate analysis or option chips. Ordinary and mixed tool records retain their real call/result pairs.
- Synthetic pairs are request-only: they do not change chat storage or execute tools. They are retained or dropped together within the context budget. The Prompt Inspector uses the server projection. Ordinary generation and the older browser route keep their existing request shapes.
- Server rounds send the same ordered list of runnable tools and force only the current tool in `tool_choice`, regardless of legacy `enforce_mode`. A step accepts exactly one fresh matching call with string `content`. Missing, invalid, unrelated, or duplicate calls fail that attempt before any action runs. Default steps pair the actual call with a short receipt; custom steps pair it with the result from the browser. Steps can override the maximum response tokens and reasoning effort for their round.
- Preset prompts can scope to a step: an `injection_trigger` value of `pipeline:<tool>` appends that material when the step is driven; earlier material remains in subsequent request prefixes. Base prompts for the selected action are captured once, not re-expanded each round. The closing round has no active step, so it appends no new step-scoped material. The prompt panel renders one `管线 <tool>` checkbox per runnable step.
- The prompt panel's bottom 回复管线 section is the step editor: one row per step (`tool`, optional `model`, and per-round `prompt`), an enable toggle, and add/delete/up/down controls. Row order IS the plan and the last row always owns `final`; edits write `oai_settings.reply_pipeline` directly (step keys the UI doesn't expose — `display`, `max_tokens`, `reasoning_effort` — survive row edits).
- Steps advance one at a time by current index, retaining logical names for tags and triggers. The server retries a failed model response within the current round before showing an error. Only the older browser path can advance on nonempty text without a tool call, retaining it without inventing a wire call or receipt.
- When the final step completes, its submitted content is the reply, including JSON-looking text verbatim. Empty or unusable results trigger one closing round with an explicit "do not call tools" instruction and, when tool definitions are available, `tool_choice: 'none'`; the failed final card's `hidden` display is lifted to `summary` so the error stays visible.
- The final-direct write keeps the AI_OUTPUT regex pass, skips stopping-string trimming, mirrors the normal generation tail (save, unblock, panel refresh), and preserves the streaming return shape.
- Cards: while a run is in flight, rounds merge into ONE live card message (matched by `extra.reply_pipeline_run` on the older browser path). On `final`, the card is folded INTO the reply — a single assistant message whose `mes` is escaped semantic tag text (`&lt;{tool}&gt;content&lt;/{tool}&gt;` per step — e.g. `&lt;analyze&gt;`/`&lt;review&gt;`/`&lt;respond&gt;`) and whose `extra.tool_invocations` carries all run invocations, including local records for text-only steps. Such a record does not mean a tool was called. Tag delimiters are escaped so tag names display literally (sanitizers would eat unknown elements); the raw tag-wrapped text is directly readable with zero regex. The last tag carries the reply raw — `<plot-options>`-style markup stays live — plus a `data-respond-options` chip row inside it. No JSON, no card chrome. AI_OUTPUT regexes restyle or strip blocks by matching `&lt;tag&gt;` entities (write-time on the whole `mes`, `markdownOnly` at display, `promptOnly` pre-send); prompt assembly drops earlier step blocks, unwraps the last tag to plain reply text, and drops the chip row. That effective body supplies the history projection above; outside projection it remains ordinary assistant text. Saved step records are not later-turn replay. Cards that mix pipeline calls with ordinary tool calls keep the structured replay so real tool results stay paired. Only on the older browser path does the closing-round reply appear as a separate normal message with the previous card left visible.
- On the older browser path, `GENERATION_STARTED` at depth 0 starts a fresh run and recursion rounds keep the active plan. On the server path, send, regenerate, or continue starts the run and later steps retain that captured plan.

## Known Limits

- Linear pipelines only; runnable steps are clamped to `MAX_PIPELINE_STEPS` (5, aligned with `ToolManager.RECURSE_LIMIT`) so the fallback round always stays inside the recursion budget.
- Every active step requires upstream support for per-function `tool_choice`; legacy `auto` does not disable forced choice, and gateways may reject unsupported requests.
- The runtime does not validate step result structure beyond the final-step extraction contract.
