# Page: Chat Workspace

## ID 解释

`page.chat_workspace` represents EmberDesk's main in-browser working surface after the root URL finishes loading. It covers the persistent shell that users stay in while switching characters, chats, and backgrounds. It does not cover standalone installation, server startup, or backend-only maintenance tasks.

## Page Purpose

- Workspace-facing events and slash reachability are internal contracts used by first-party modules.

This page exists so a user can run their daily LLM workflow from one browser surface: choose a character, open or continue a chat, and adjust surrounding workspace context without leaving the main shell.

## Page Structure (UI Layout)

1. **Primary shell frame**: the always-present application chrome that becomes usable after the startup overlay disappears.
2. **Character and navigation region**: the area where users browse character cards, search/filter the library, enter bulk edit flows, and switch the active working context.
3. **Main chat region**: the central conversation surface where messages, generation output, and chat actions are shown. Each user turn—including tool results, pipeline output, and the final answer—is presented as one continuous visual card while retaining the original message rows and actions.
4. **Supporting panels and drawers**: secondary UI surfaces for the prompt preset panel (left side drawer), World Info, and Regex. Active chat background selection remains part of chat context, not a library drawer.
5. **Composer and action region**: the place where users type prompts and trigger chat actions, with the primary textarea, send button, stop/continue/impersonate actions, and chat-options entry discoverable through stable roles and accessible names.

## Page States And Constraints

- **New-chat greeting state**: loading an unused character chat offers an opening-greeting picker for the default greeting and Alternate greetings, and starting a new chat opens that picker immediately when multiple greetings exist. Search summaries show matching text in context, the preview stays within matching candidates, and no results disables confirmation. The picker distinguishes the currently used greeting from the preview and names the greeting in its confirmation action. When switching remains allowed, compact previous/next controls apply the adjacent valid greeting directly, and the focused picker trigger also responds to `ArrowLeft`/`ArrowRight` with circular traversal; empty greeting entries are skipped. These quick-switch controls are disabled while the greeting is being saved, and the explicit picker and quick-switch path share the same chat replacement and persistence behavior. Arrow keys keep their normal cursor-editing behavior when a search or text input has focus. On narrow screens, selecting a character closes the character drawer so the chat controls remain reachable. Only confirming a selection or using a quick-switch control saves the greeting to the chat; cancelling writes nothing, and choosing a greeting never changes the character card. Once dialogue starts or Continue is used, the greeting can no longer be replaced. The selected greeting's full text survives refresh and is not overwritten when the character card is saved.
- **Settings navigation state**: the React workspace shell's single `设置` entry opens the in-workspace [Settings](page.settings) top-center drawer, restoring the last-used tab. Direct `/settings?tab=...` remains the full-page deep-link path. The drawer hosts the merged Frontend Frames 消息渲染设置 fields inline on the providers page — the former `user-settings-block` drawer is retired. The drawer refuses to close while the surface reports unsaved edits (nav entry, sibling-drawer mutual exclusion, or Escape all confirm before discarding a dirty form or an unsaved API-key draft).
- **Shell ownership state**: `/` always starts the React shell; operational rollback uses a prior release.
- **Child-slot state**: Prompt Preset Panel, Character Library, World Info, Character Authoring, Regex, and the Main Chat regions retain stable protected DOM only as declared child content or compatibility hosts. Character Authoring is entered from Character Library's create/edit actions, not from shell navigation. Their legacy classes do not own shell navigation or pin state.


- **Startup state**: the shell is not yet interactive while the startup overlay is still visible.
- **Ready state**: the main shell becomes usable before every supporting panel has necessarily finished background loading.
- **Degraded state**: if a supporting surface such as world info or backgrounds fails to load, the core shell can still remain usable and the affected panel shows local retry or follow-up refresh behavior.
- **Thumbnail paint state**: avatar-heavy list surfaces can show a theme-tinted placeholder on the image box before thumbnail pixels fully paint, reducing harsh flashes without changing the page flow. Static image templates use explicit default placeholder assets (`img/No-Image-Placeholder.svg` or the user-avatar default) so an uninitialized dynamic image does not begin as an empty or broken `src`.
- **Thumbnail cache state**: newly regenerated JPEG thumbnails only pick up the lower shipped default after two separate conditions are satisfied where relevant: an existing install with an explicit `thumbnails.quality` override must first change or remove that config value, and already-cached thumbnail files must still be cleared before regeneration can produce lower-quality replacements.
- **Post-write thumbnail warm state**: after character-avatar writes succeed, EmberDesk can kick off best-effort thumbnail pregeneration in the background so the next normal workspace revisit is less likely to stall on first thumbnail generation; if that background work fails, the existing on-demand thumbnail route still remains the fallback.
- **Managed media compatibility state**: uploaded images and chat attachments keep their established workspace paths and thumbnail behavior. When their managed catalog is enabled and verified, EmberDesk can retain their identity and lifecycle through that catalog without changing the URLs used by the workspace; when it is disabled or requires repair, the compatible file paths remain available through the existing file-backed path. Managed attachment paths that no longer resolve through that catalog now fail before a canonical chat save is committed instead of creating a new hidden dangling reference.
- **Current-chat text maintenance state**: the open session's message text and reasoning text can be rewritten through [Character Text Replace](feature.character_text_replace) from Character Authoring; the feature refuses to apply while a reply is generating and reloads the current chat afterward so the stale in-memory copy cannot overwrite the applied result.
- **Chat persistence compatibility state**: after the chat storage migration is verified, character chats still open, export, save, rename, delete, and import through the same workspace controls. The browser receives the complete history used by load-more, with the same message order, swipes, metadata, events, renderer ownership, slash commands, and row actions; the migration adds no server pagination. Character-chat search/recent reads canonical session/query state after a clean chat audit while preserving the same response shape, pinned ordering, metadata, and root-chat recent fallback. If projection repair or validated restore is needed, the visible chat result remains coherent and operators complete recovery without exposing storage controls or governance notices in the workspace. Out-of-band file edits do not silently replace the chat a user has saved through the workspace.
- **Character-library owner state**: the character library stays on the same workspace entry, and the React panel is the sole runtime owner for the visible toolbar, list, selection, and bulk-browsing surface. There is no Character Library product flag or legacy list fallback; release validation must ship the React bundle, and a missing bundle fails closed with a visible build error. Operational rollback is deployment of the previous application version.
- **Active background state**: the workspace can apply a global active background setting and a chat-specific `custom_background`/`chat_backgrounds` override. Removing the chat override returns to the global active background without turning either state into a global gallery.
- **Background and identity state**: the workspace does not expose a global background gallery or sprite controls; static background paths, avatar images, and retained thumbnail behavior remain separate compatibility capabilities. There is no persona management: user messages render under the fixed default user identity.
- **Supporting-panel migration state**: World Info continues to open from its existing workspace entry. Their visible React ownership and protected compatibility slots remain documented by their own features.
- **Workspace panel dock coordination state**: When the same-entry React chrome is mounted, Prompt Preset Panel, Character Library, World Info, and Regex entries publish transient active-panel/dock state. Character creation and editing are subflows of Character Library, rather than a second top-level entry. The chrome shows only the selected assistant, or character name for current context, using `EmberDesk` for the default assistant; it does not repeat chat type, chat ID, message count, temporary-chat state, workspace-ready, or panel-ready/status copy. The active entry remains the visible confirmation that a panel is open; errors and recovery actions remain inside the affected panel. Clicking the active entry closes the established surface when the owner reports that it closed; clicking it again reopens it from the same entry. The unified `设置` entry uses the same transient dock state while presenting the shared [Settings](page.settings) owner as an independent overlay rather than a drawer or route transition. The latest manual open and refocus intent is remembered only in the current browser page session, so a refresh or remount in that same session does not immediately discard the user's last panel choice while still avoiding a new long-term preference. The shell chrome renders no pin control; drawer pinning is owned by each drawer's own lock toggle (`.pinnedOpen`, persisted via accountStorage), and clicking an active entry does not close a locked drawer.
- **Main-chat owner state**: React is the sole runtime owner of the main-chat message list inside the existing `#chat` surface. `app/stores/main-chat-store.ts` owns the typed message snapshot, ordering, visible window, generation/streaming snapshot shape, and transient row state; React emits direct-child `.mes[mesid]` rows, `#show_more_messages` ordering, reading-position restoration, swipe wrappers, `.mes_buttons`, and reasoning shells. There is no product flag that restores a dual-owner legacy list renderer; missing workspace-panels builds fail closed with a visible build error, and rollback is previous-version deploy. React visible rows call named commands for edit/copy/delete/move/retry/swipe, reasoning expand/copy/edit/delete/collapse, and composer generation entry points. Reasoning row commands persist `chat[].extra.reasoning` and emit supported events without reading message DOM; parsing/templates and stream-state behavior remain compatibility-owned. `public/scripts/main-chat-composer-service.js` is the typed owner of the composer text value: every programmatic read/write (submit flows, STscript clears, `/input`, `{{input}}`, impersonate injection, the React `submitMessage` command) flows through its command functions, while the React-rendered uncontrolled `#send_textarea` is a render detail and native `input` events sync user typing into service state. One framework-neutral generation service owns request assembly, streaming lifecycle, stop, bounded recovery, fallback attempts, and final results for visible direct, provider-specific, dry-run, nested, quiet, and background requests. The compatibility `Generate()` entry continues to accept existing callers but delegates to that service. Quiet and background helpers remain non-visible, create no assistant row, return generated text, and do not auto-retry. Framework-neutral `chat-message-render-service` produces formatted HTML without owning DOM insertion; React rows consume that service for supported lifecycle states. Compatibility aliases such as `printMessages` / `showMoreMessages` / `updateMessageElement` may remain as thin adapters for callers, but they are not product dual-owner list/windowing surfaces. The hidden controller retains layout, local-status, windowing, and row-lifecycle diagnostics. There is no separate `#jump_to_latest_message` control.
- **Main-chat reading-position state**: after the user scrolls within a chat or expands older history, leaving that chat and returning in the same browser page session should restore the prior reading region. If the saved anchor can no longer be reopened safely, EmberDesk falls back to the normal open result instead of leaving the chat in a half-restored state.
- **Character-library oversized state**: if eager character-library loading reaches the configured data length limit, the workspace shows the existing guidance to enable lazy character loading and restart instead of leaving the library failure unexplained.
- **Character data transparency state**: the workspace keeps the same visible character-library and current-card behavior instead of exposing hidden cache/index maintenance steps to the user.
- **Post-delete consistency state**: after a character is deleted, stale delayed saves, edit responses, or late character-library query snapshots for that card should not restore it into the visible library.
- **Temporary chat state**: when the user opens a temporary Assistant chat, the workspace shows a visible temporary-chat status near the current-character title area; it is cleared when a normal character context is selected or a permanent Assistant chat is opened.
- **Post-active-delete safe state**: after deleting the active character, the selected-character title area must route to a safe empty or library state rather than trying to reopen the deleted card.
- **World Info panel state**: the World Info drawer keeps global activation controls separate from the editor selector; empty global selection and editor selection states must not leave stale entry content visible. When the guarded React World Info panel is mounted, React is the sole visible workbench owner inside the same drawer entry (no independent route); legacy DOM remains the hidden adapter and flag-off/build-failure fallback. Locked Character Management still coexists while World Info is open.
- **Group chat state**: the workspace does not expose group chats, group authoring, or multi-character generation. Stale `/api/groups/*` and group write paths fail with ordinary `404`/request rejection. Existing on-disk `groups/` and `group chats/` files are left untouched and are not auto-purged.
- **Regex editing and import state**: the first-party Regex editor validates script name, regular-expression syntax (static patterns), and affected areas before saving; invalid drafts stay open with field-associated errors. Narrow screens stack option groups and use touch-sized controls. Import shows global/preset/character scope and the current target context, disables unavailable targets, and performs no import on Cancel, Esc, or close. The debugger disables test/order actions without rules, offers rule creation, and displays output sections only after a test.
- **Vector state**: the workspace does not expose vector storage or vector prompt itemization. Data Bank attachment management remains available, legacy vector indexes remain untouched derived data, and stale `/api/vector/*` callers receive ordinary `404` responses.
- **Token-inspection state**: the workspace does not expose per-message prompt itemization or a logprobs viewer; stored per-chat itemized-prompt data remains on disk as inert data. Request-level inspection is provided by [Prompt Inspector](feature.prompt_inspector): an unsent preview of the next request body assembled through the real generation path, not message-level itemization.
- **React chrome navigation state**: When the React workspace chrome is mounted, `提示词`, `角色库`, `世界书`, `正则`, and `设置` are the visible primary navigation entries. The `提示词` entry opens the left prompt preset drawer and the `角色库` entry opens the right character drawer; on accounts with no stored drawer preference both side panels start open and pinned, while an explicit stored close or unlock persists across reload. `设置` opens the React [Settings](page.settings) surface as an in-workspace overlay on the last-used tab. `oai_settings` values persist without a dedicated generation-tuning surface, and drawer pinning remains only on the surviving drawers' own lock toggles. Direct `/settings` remains available as a deep-link full-page mount. Character Library owns the create/edit entry points for React character forms; React remains the sole owner for character create/edit fields and direct save commands. Missing workspace-panels builds fail closed; previous-version deploy is the rollback path.
- **React panel entry accessibility state**: Registry-backed entries remain role/name reachable and expose active pressed state while the active panel status remains a local shell/panel signal rather than global workspace loading.
- **First-open panel state**: Opening World Info or Character Library from the React chrome should succeed on the first click without freezing the visible workspace. Active background application remains available through chat context and metadata.
- **Internal runtime surface state**: `globalThis.SillyTavern`, `eventSource` / `event_types`, and `/lib.js` remain internal infrastructure for first-party modules; `__emberDeskReactCompatibilityBridge` stays internal-only.
- **Shared-library state**: the workspace loads a shared browser library during startup so first-party modules can use documented imports and shared globals without each surface bundling its own copy.
- **Message rendering state**: stored or finalized messages render into stable `.mes[mesid]` rows with readable `.mes_text`, while message-row actions remain attached to the rendered row.
- **Generation failure recovery state**: when generation fails after a user message or partial assistant output, the workspace keeps the existing rows readable, restores composer input, and exposes a local recovery action instead of requiring a refresh.
- **Automatic recovery state**: visible main-chat generation can retry once on the primary provider and once on the optional fallback provider before the existing manual retry CTA appears.
- **Generation control bridge state**: when the guarded React main-chat flag is enabled, the hidden controller exposes the current generation and streaming phases for tests and diagnostics. Those phases describe the unified command/lifecycle service rather than a React-versus-legacy transport handoff.
- **Streaming, composer, slash, and quiet-helper bridge state**: the composer keeps the established `#send_textarea` / `#send_but` selectors and routes submit, stop, continue, and regenerate through named command capture while the typed snapshot is projected into React; the composer text value is owned by `main-chat-composer-service` rather than the DOM node. React renders the typed slash autocomplete and paused/aborted/error status shell, while the slash parser, registry, executor, and public exports remain compatibility-owned; streaming diagnostics remain available for tests; quiet/background requests retain their non-visible, no-row, return-string behavior without separate owner markers.
- **Composer input and draft state**: the composer field renders as a bordered recessed input with a left-aligned placeholder. A persistent hint line and an open-connection-settings link appear only while the workspace reports no API connection, and a send attempted while disconnected flashes the composer border and warns instead of failing silently; while generating, the stop control reads in the warning color. The chat-options menu exposes an `附加文件` (Attach a File) entry that opens the established attachment flow alongside paste and drag-and-drop. Pending composer text is kept per chat and restored when the user returns to that chat, rather than carried into whichever chat opens next.
- **Long-chat load-more state**: after the user loads older messages from a bounded long-chat window, the workspace preserves loaded history and message IDs without adding a separate return-to-newest control.
- **Mobile reachability state**: core composer controls, message actions, long-chat load-more, and generation stop or retry controls should remain visible or keyboard/role reachable on narrow phone and wider mobile/tablet viewports without relying on hover-only discovery.
- **Chat management accessibility state**: Chat History is a named native modal dialog with a labelled search field; long filenames truncate within the row rather than pushing rename/export/delete controls off-screen. Chat options use full-width single-column actions and announce their expanded state. History and backup controls use at least 44px touch targets on narrow/coarse-pointer devices.
- **Options-menu regenerate state**: the chat-options menu carries a `重新生成` entry ([Chat Turn Regenerate](feature.chat_regenerate)) that is disabled while generating, editing, disconnected, or in an empty chat; its availability is recomputed each time the menu opens so a stale projection can never start a second generation.
- **Backup browser state**: opening Backups shows loading, empty, or recoverable error states. View/restore/delete operations show progress and prevent duplicate submissions. Backup previews and deletion confirmations are named native modal dialogs with contained keyboard focus and focus restoration. Deletion names the backup file and leaves its confirmation open with an error if the request fails; restoring a backup imports it as a chat rather than deleting the current chat.
- **Chat rename state**: the rename input is associated with its dialog heading. Blank names and failed rename requests keep the local draft visible with an inline error so the user can correct it or retry. Chat-file deletion and new-chat confirmations name the action instead of generic Yes/No choices.
- **Auxiliary dialog state**: Generic text, confirmation, and error dialogs keep long content vertically scrollable while actions remain reachable. Expanded editors carry the source field name, focus the text area, and explain that edits write through immediately; Done or Escape closes the view without reverting those edits.
- **Avatar and media preview state**: Avatar previews expose a named keyboard-reachable close button and an image description. Avatar cropping supports named move, shrink, enlarge, and reset buttons without requiring pointer dragging. Image previews expose a named zoom button and retain the close action when zoomed; interacting with video controls does not dismiss the preview.
- **Macro browser state**: The React macro browser has a labelled translated search, explicit empty/no-match feedback, a clear-search recovery action, announced selected/sort states, and readable low-intensity selection colors. Narrow containers stack the list and details vertically; signatures and descriptions wrap. The search index is reused across query changes.
- **Media and style preference state**: External media remains forbidden by default, with per-character allow/forbid overrides. Media and Creator's Notes style preferences explicitly say that changes apply immediately and use Done to close. First-time style authorization presents two explicit scope actions; applying styles to the whole application is not a cancel action, and dismissing the question chooses the limited scope. Quota errors refer to the configured model service, not an assumed OpenAI account.
- **Action loading state**: Blocking operation dialogs announce the task name and busy state. Available stop controls are named native buttons with at least 44px targets; loading notifications use the workspace theme rather than a separate bright toast palette.
- **Mobile panel dock state**: On narrow viewports, React navigation remains icon reachable without panel-status copy consuming chrome width or covering the composer; drawer content and protected message surfaces remain reachable through the existing mobile layout rules.
- **Settings missing-build state**: if the React app build for [Settings](page.settings) is missing, `/settings` fails closed with HTTP 503 rebuild instructions instead of returning users to workspace legacy settings drawers.

## Ownership Notes

React surfaces are sole runtime owners where mounted; main-chat command execution is unified behind the framework-neutral generation service. Rollback is deployment of a prior version rather than a live transport fallback.

## Navigation

- The workspace is the product's main destination and root route.
- From this shell, users can move between the character library, chat context, and World Info without leaving [Chat Workspace](page.chat_workspace). The former global Background Library does not introduce a replacement route or panel.
- React [Settings](page.settings) is the sole product owner for provider, UI, and advanced settings; the React shell `设置` entry opens the same Settings surface as an in-workspace overlay instead of leaving chat or opening the old forms. Specialized World Info, active chat backgrounds, and avatar media remain on this workspace.
